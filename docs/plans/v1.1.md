#### `history_(req)`

Request: `{ before, days, tables? }`.

- `before` is required and must `Date.parse` to a finite number. Otherwise `bad_record`.
- `days`: `Math.min(90, Math.max(1, parseInt(req.days, 10) || 30))`. Omitted, `0`, or non-numeric becomes 30. Above 90 becomes 90.
- Window is half-open in milliseconds: `[before - days * 86400000, before)`. This is 24-hour blocks, the same unit as `read`. It is not Taipei calendar days. Care due dates use calendar days elsewhere. Do not mix them.
- Include deleted rows. Do not skip `deleted === true`.
- `tables` omitted, or `[]`, means every `LOG_TABLES` entry, including `Care`. A non-array is `bad_record`. A name not in `LOG_TABLES` (including `Foods` and `Config`) is `bad_table`.
- A row with an unparseable `ts` is not in the window and does not make `hasMore` true.
- `hasMore` is true when any requested table has a parseable `ts` strictly less than `from`.
- Response:

```js
{
  ok: true,
  version: 2,
  tables: { /* only requested tables, rows passed through strip_ */ },
  from: /* Taipei ISO of (before - days), same formatter as serverTime */,
  before: /* Taipei ISO of the parsed before */,
  hasMore: true | false
}
```

Do not return Foods or Config. The client must send the next request with `before` equal to this response's `from`, so windows chain with no gap.

#### `getPhoto_(req)`

Request: `{ fileId }`.

- Missing or empty `fileId` → `bad_record`.
- No `PHOTO_FOLDER_ID` → `no_folder` (same wording style as `uploadPhoto_`).
- `DriveApp.getFileById` throws, or the id is a folder, or the file has no parent equal to `PHOTO_FOLDER_ID` → `{ ok: false, error: 'forbidden', message: '讀不到這張照片' }`. Do not return `server_error` for a missing file. Do not include the id in the message.
- Parent check is mandatory. Walk `file.getParents()` and compare ids to `PHOTO_FOLDER_ID`. A file that merely exists in Drive is not enough.
- Success: `{ ok: true, mime: blob.getContentType(), data: Utilities.base64Encode(blob.getBytes()) }`.
- Do not log the base64.

`uploadPhoto_` stays as it is. New files are created in `PHOTO_FOLDER_ID`, so `getPhoto` can read them.

```ts
export type DueKind = "overdue" | "today" | "soon" | "later" | "never"

export function dueKind(daysLeft: number | null): DueKind {
  if (daysLeft === null) return "never"
  if (daysLeft < 0) return "overdue"
  if (daysLeft === 0) return "today"
  if (daysLeft <= 3) return "soon"
  return "later"
}

export function dueText(daysLeft: number | null): string {
  if (daysLeft === null) return "還沒記錄過"
  if (daysLeft < 0) return `已逾期 ${-daysLeft} 天`
  if (daysLeft === 0) return "今天到期"
  return `還有 ${daysLeft} 天`
}
```

The threshold is 3 for the whole app. `1` is「還有 1 天」, not「明天」.

Summary line for the three items:

- Count `overdue` (`daysLeft < 0`), `soon` (`0..3`, including today), and `never` (`null`).
- If overdue count and soon count are both 0: start with `都還沒到期`. If never count is > 0, append `・N 項還沒記錄過`.
- Otherwise join the non-zero pieces with `・`, in this order: `N 項已逾期`, `N 項快到期`, `N 項還沒記錄過`.

Last-done line:

- No row: `點右邊的按鈕記第一次`.
- `dayDiff(last.ts, now) === 0`: `上次：今天・${who}`.
- `=== 1`: `上次：昨天・${who}`.
- Same calendar year: `上次：${fmtDate(last.ts)}・${who}`.
- Other year: `上次：${fmtFullDate(last.ts)}・${who}`.
- If `last.sync === "queued"`, the row also shows an info-colored `CloudOff` (16px) and `・待上傳`. If `sync === "failed"`, show `沒送出` the same way `TimelineItem` does.

```ts
export function firstBefore(serverTime: string, days: number, now: Date): string
```

`Date.parse(serverTime) - days * 86400000`, formatted with `toTaipeiISO`. If `serverTime` does not parse, use `now`.

Pager state lives in the React layer (Main, or a hook used only by Main), not in the sheet:

```ts
type Pager = {
  hasMore: boolean
  loading: boolean
  error: null | "offline" | "fail"
  suppressAuto: boolean
  inflight: boolean
}
```

`loadOlder()`:

1. If `!supportsV11(data.version)`, return and do not call the adapter.
2. If `inflight`, return.
3. If `navigator.onLine === false`, set `error: "offline"` and return.
4. `before` for the first call is `firstBefore(snap.serverTime, snap.days, now)`. Later calls use the previous response's `from`. Do not recompute.
5. If that `before` is already in `fetchedBefores`, return.
6. Call `api.history({ before, days: 30 })` once. Do not pass `tables`.
7. On success, `absorbHistory`, set `hasMore` from the response, clear `error`. Compare the filtered visible count before and after the merge. If it did not increase, set `suppressAuto = true`. Deleted rows count as visible. Duplicate ids do not.
8. On `NetworkError` while offline, `error = "offline"`. Any other failure, `error = "fail"`. Leave already loaded rows in place. Remove the cursor from `fetchedBefores`. Do not auto-retry.
9. The 2-minute `refresh()` must not call `loadOlder`.

Changing the filter clears `suppressAuto`. A manual tap on「看更早的紀錄」also clears it and then calls `loadOlder`.

End-of-list priority, exactly one:

1. `version < 2` → update note, even when offline.
2. `loading` → skeletons.
3. `error === "fail"` → failure alert.
4. Offline and `hasMore` is not known-false → offline alert.
5. `hasMore === false` → end copy.
6. Otherwise the load-more button.
