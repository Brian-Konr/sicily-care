# v1.1.1 照片顯示修正（spec）

## 現象
線上 v1.1，Brian 2026-10-09 14:57 用 iPhone PWA 送的異常（類別「其他」，備註「可愛的很嚴重」），在異常詳情的縮圖是 iOS 破圖「?」。
Drive 上的檔案 `image.jpg` 是有效 JPEG（FFD8…FFD9、JFIF+Exif、465,668 bytes），在 Drive 開啟正常，所以上傳端沒問題。
後端 `getPhoto_`、`respond_`、`api.getPhoto`、`useIssuePhotos` 的程式碼都看不出錯：回 `{ok, mime, data}`，前端組 `data:${mime};base64,${data}`。

## 已知的漏洞（一定要修）
1. `useIssuePhotos` 拿到回應就設 `ready` 並 `cache.put`，**完全沒驗證**能不能解碼。壞資料會變破圖，而且永久卡在 IndexedDB。
2. 用 600 KB 以上的 data URL 塞進 `<img>`；iOS standalone PWA 對超長 data URL 與記憶體很敏感，是最可能的實際原因。

## 修法
- `getPhoto` 回應先驗：`mime` 必須是 `image/(jpeg|png|webp)`；`data` 必須是合法 base64、長度 > 0；解出 bytes 後檢查 magic（JPEG FFD8FF、PNG 89504E47、WebP RIFF....WEBP）。不合格 → `error`。
- 顯示改用 Blob：base64 → `Uint8Array` → `Blob` → `URL.createObjectURL`。不再把長 data URL 放進 `<img>`。元件卸載或換照片時 `revokeObjectURL`。
- 標成 `ready` 之前先解碼確認：`createImageBitmap(blob)`（不支援時用 `new Image()` + `img.decode()`）。失敗 → `error`，**不寫快取**。
- 快取存 Blob（或 bytes），不存 data URL。DB 名稱改成 `sicily-photos-v2`，並在開啟時刪掉舊的 `sicily-photos`（自動清掉壞快取）。
- 讀快取命中時同樣要解碼確認；失敗就刪掉那筆、重新向後端取一次。
- `PhotoThumb` 與 `PhotoViewer` 的 `<img onError>`：把該張設成 `error`，並刪掉它的快取。`error` 狀態沿用現有文案與「再試一次」，按下會跳過快取直接重抓。
- 本機待傳照片（`local`）維持現狀，但同樣加 `onError` → `error`。
- 加一個診斷：`error` 時在 `console.warn` 記下原因（`bad_mime` / `bad_base64` / `bad_magic` / `decode_failed` / `img_error`）與 bytes 長度，不記內容。

## 不做
- 不改後端回傳格式、不改上傳與壓縮、不改 `appsscript.json`、不加依賴。後端不用重新部署。

## 測試
- photo 解析純函式：合法 JPEG/PNG/WebP 通過；空字串、非 base64、錯 mime、錯 magic、截斷（只剩前 100 bytes 的 JPEG 仍有 magic 但解碼失敗，用注入的 decoder 模擬）→ 各自的錯誤碼。
- useIssuePhotos（或抽出的 loader）：解碼失敗 → `error` 且未呼叫 `cache.put`；快取命中但解碼失敗 → 刪快取、重抓；`retry` 跳過快取。
- photoCache：舊 DB 名稱會被刪；存取 Blob。
- `npm test`、`npm run build` 全過。

## 驗收
1. 單元測試涵蓋上面所有錯誤路徑。
2. 本機試用模式：正常照片照常顯示（縮圖與全螢幕）；把 mock 的 getPhoto 改回一段截斷資料時，縮圖顯示 error 文案與「再試一次」，不是破圖。
3. 部署 gh-pages 後，Brian 的 iPhone 重開 app，14:57 那筆的照片能看到；若仍失敗，至少顯示 error 狀態，並回報 console 診斷碼（Ningning 用 Safari 遠端檢查或請 Kazuha 協助）。
