## 0. 相容性原則（先讀）

- **需要 Brian 更新 Apps Script。** 原因是有新分頁 `Care`，還有新的 action `getPhoto`、`history`。只要每個人都照第 6 節的步驟做，網址不變，授權範圍也不變。
- **前端要能先上線。** `read` 的回應會新增 `version: 2`，舊後端沒有這個欄位。前端看到 `version < 2` 時，新功能一律顯示「需要更新 Apps Script」的提示，不可以送出會失敗的請求，也不可以讓整個 App 壞掉。品項封存只用到既有的 `upsertFood`，不受影響。設定頁的三個新間隔，在舊後端也**照常可以改**，因為舊版 `setConfig` 本來就接受任意 key。
- 寫入照舊遵守 `decisions.md` 第 8 到 13 條：請求最長等 55 秒、前端先產生 `id` 保持冪等、有離線佇列、用 `LockService`、只做軟刪除。

## 1. 貓砂盆整盆清洗（週期）

- 新紀錄分頁 `Care`，欄位：`id, ts, who, deleted, kind, note`。`kind` 只有三種：`litter_wash`、`feeder_clean`、`feeder_desiccant`。
- 和每日鏟砂（`Litter`）完全分開。Chaewon 讀 `Care` 就知道上次清洗是什麼時候。
- 下次日期＝這個 kind 最後一筆未撤銷紀錄的 `ts` 加上間隔天數，用台北時間的日曆日計算。不另外存 `next_due`。紀錄的日期可以在編輯時改（補記用）。
- 顯示「還有 N 天」「今天到期」「已逾期 N 天」，規則照 DESIGN.md §7.3 的 `DueStatus`：逾期用紅點加文字，今天到期或 3 天內用 warning 色，其他用灰字。Med 畫面原本寫「逾期 N 天」「N 天後」，這次一起改成同一套文案和元件。從來沒有記錄過時，顯示「還沒記錄過」，不要算成逾期。
- 一鍵完成：點「已清洗」就以現在時間記一筆，不用再確認。記完顯示「已記錄＋撤銷」，跟其他一鍵紀錄的行為一樣。

## 2. 自動餵食器：清潔、換乾燥劑

- 兩個獨立的追蹤項，`feeder_clean` 和 `feeder_desiccant`，規則跟第 1 節完全相同。
- 新的 Config 預設值：`litter_wash_int_days=30`、`feeder_clean_int_days=30`、`desiccant_int_days=30`，可以在設定頁修改。這三個 key **可以**加進前端和 GAS 的 `DEFAULT_CONFIG`，因為它們沒有「沒有這個 key 時代表另一種意思」的問題，和 `birthday_estimated` 不一樣。
- 位置和外觀由 Winter 設計。Lead 建議首頁加一張「居家維護」卡片，三列各有剩餘天數和一個一鍵按鈕，不要再增加第六顆大按鈕。

## 3. 異常回報：詳情和照片

- 異常列表的每一筆都可以點進詳情頁，顯示類別、細項、嚴重度、誰、什麼時候、備註、是否已解決，以及照片（最多 3 張）。點照片會全螢幕顯示，可以雙指放大、左右切換。
- **照片不要直接用 Drive 網址嵌入。** iPhone 加到主畫面的 PWA 跟 Safari 不共用 Google 登入，Mia 很可能看不到。改成新的 action：
  - `getPhoto { fileId }` 回傳 `{ ok, mime, data(base64) }`
  - 後端**必須檢查這個檔案在 `PHOTO_FOLDER_ID` 資料夾裡**，不在就回 `forbidden`。腳本有完整的 Drive 權限，不檢查的話，只要有密鑰就能讀 Brian 整個 Drive。
- 前端採用延遲載入：進到詳情頁才抓照片，載入中顯示佔位，失敗可以重試。抓到的照片在這支手機上快取（IndexedDB 或 Cache Storage 都可以，上限約 50 張，舊的先刪）。
- 另外保留一個次要的「在 Google Drive 開啟」連結（`photo_urls`），當作備用方式。
- 照片如果還在手機的「待傳」清單裡，就直接顯示本機的那份。
- 同一個照片元件之後清砂紀錄也能用，但 v1.1 只要求異常回報。

## 4. 完整歷史紀錄

- 時間軸從「最近 7 天」改成可以一直往前捲。按日期分組，台北時間，日期標頭寫成「9 月 24 日（四）」。分頁名稱「7 天紀錄」改成「紀錄」，首頁的「看 7 天 ›」改成「看全部 ›」。
- 頂端用類型篩選晶片：全部、副食/零食、清砂、體重、驅蟲/疫苗/用藥、異常、居家維護。可以多選，預設是全部。
- 新的 action：`history { before, days, tables? }`
  - 回傳 `ts` 在 `[before − days, before)` 之間的紀錄，**包含已撤銷的**，因為時間軸要能復原。
  - `days` 預設 30，最多 90。`tables` 不給就是全部紀錄分頁。
  - 回應格式：`{ ok, tables: {…}, from, before, hasMore }`。`hasMore` 代表更早還有沒有資料。
- 第一頁直接用首頁已經載入的 7 天資料。往下捲到底時，抓下一個 30 天區間。已經抓過的區間這次開著 App 時記在記憶體裡，不重抓。
- 篩選只在前端做，不用為了篩選重新向後端請求。這樣每一頁永遠只有一個請求。
- 載入中、沒有更多、離線（顯示「需要連線才能看更早的紀錄」）、失敗重試，這四種狀態都要有。
- 舊紀錄的撤銷、復原、編輯，行為和 7 天時間軸一樣。
- 首頁的 `read` 維持 7 天，不變。
- 歷史列表裡的列不連到異常詳情頁，異常詳情只從異常畫面進入。

## 5. 副食/零食品項封存

- 位置：副食/零食畫面裡有一個「管理品項」清單，入口由 Winter 決定。清單裡往左滑會出現「封存」，**另外要有不用滑也能操作的方式**，例如每列的「⋯」選單，因為滑動不是每個人都會、也不一定好按。
- 確認對話框的文字：「封存『雞肉絲』？之後不會出現在選單裡，過去的紀錄會保留。」後面再加一句「需要時可以在下方「已封存」恢復。」按鈕是「封存」和「取消」。
- 實作是 `upsertFood { food_id, active: false }`，用既有的 action，**不硬刪**。舊紀錄本來就存了 `food_name`，名稱不會消失。
- 品項選單、最近使用、收藏都要排除 `active=false` 的品項。清單最下面有「已封存（N）」，可以展開，也可以「恢復」。
- 封存最後一個品項時要允許，但選單要顯示「新增品項」的入口，不能變成空白卡住。
